Automating a job search: from scraping to outreach

A job search is a data pipeline wearing a trench coat: scrape postings, score them against a resume, track state so nothing repeats, and draft outreach that's actually worth reading. This is what I built, what didn't work the first three times, and what changed once the feedback loop included a skeptical reader.

By Oreoluwa Fagbamiye Personal project 2026 ~10 min read
Apify actors Claude Artifacts MCP connectors Prompt engineering Cloud scheduling Python

Abstract

This project scrapes job postings from two boards through Apify actors, scores each one against a resume using a keyword-coverage heuristic tuned to filter out seniority and off-topic noise, and tracks every posting's status in a dashboard that is a real stateful app rather than a static report: it reads and writes a shared database, calls a user's own Gmail and Calendar accounts directly through OAuth-scoped connectors, and drafts personalized outreach on demand. The interesting engineering problem turned out not to be the scraping. It was getting a language model to write a cold email that a specific, skeptical human would actually respond to, which took several complete rewrites of the prompt and, eventually, a second model call whose only job is to read the first draft and argue with it.

01The actual problem

Job searching at any real volume is a tracking problem before it is a writing problem. Postings repeat across boards, application statuses live in your head or nowhere, and the parts that actually take judgment (does this posting fit, and what should I say to this specific hiring team) are exactly the parts that get skipped when you are doing everything by hand at 11pm. The goal was to automate the mechanical parts completely and keep a human decision point in front of anything that leaves the system, while still letting the writing be genuinely tailored rather than a mail-merge.

02Architecture

Scraping
Apify actors for two job boards, run against a fixed list of target titles, deduplicated by URL into a persistent tracker
Scoring
Python heuristic: keyword-coverage against the resume, plus seniority and off-topic title filters, plus a location/remote filter
Dashboard
A published app (not a static page) with a shared database, connector calls to Gmail/Calendar, and on-demand AI drafting
Scheduling
A cron-triggered cloud agent re-runs the scrape/score/publish cycle on an interval and commits state back to a repo

Each stage writes to a small set of JSON files that the next stage reads, which sounds almost too simple to mention, except that it is the reason the whole thing can be re-run safely. The tracker is keyed by posting URL, so a re-scrape only ever adds what is new; nothing gets re-processed, re-scored, or re-surfaced once it has a real status attached to it.

03Scoring fit without an LLM call per posting

Running every scraped posting through a language model to judge fit would work, but it is slow and expensive at volume, and it is genuinely unnecessary for triage. Instead, fit is a keyword- coverage score: a shared taxonomy of terms (tools, certifications, methodologies) is matched against both the resume and each posting's description, and the score is the fraction of the posting's matched terms that the resume also covers.

The first version of this was too generous. A posting that happened to mention four or five common terms could hit 100% on a handful of matches, which meant senior and completely unrelated roles were scoring as strong fits purely because the denominator was small. The fix was raising the minimum number of matched terms required before a score is trusted at all, and adding a separate title-based filter for seniority language and off-topic roles before scoring even runs. A heuristic like this is a triage tool, not a verdict, and it is worth being honest about that in the UI rather than presenting a percentage as more certain than it is.

04A dashboard that is an app, not a report

The interesting decision here was refusing to let the dashboard be a static rendering of the tracker data. It is a published app with its own small database, and it declares three runtime capabilities: shared state that persists across sessions and devices, connector access that lets the page call a signed-in user's own Gmail and Calendar accounts directly (the app never sees the credentials, only the result), and on-demand model calls for drafting.

That combination means a selection made in the dashboard, a recruiter contact typed into a field, or an application marked complete is durable and visible from any device without a separate backend to run or pay for. Marking something as applied triggers a real calendar event on the user's own calendar, using their own OAuth grant, initiated by their own explicit click. No action fires automatically from a background process; every connector call traces back to a user gesture.

05Prompting for emails that get replies

This is where most of the actual iteration happened, and it is worth walking through because the failure modes were not subtle once I could name them.

First pass: generic

The first prompt asked for a short, personalized email using a handful of resume highlights. What came back was competent and interchangeable, the kind of email that could have been sent to five different companies without anyone noticing. It named general skill categories instead of the specific tools a posting actually listed, and it closed with a passive line like "I'd welcome the chance to discuss further," which asks for nothing and is trivially easy to ignore.

Second pass: evidence, not adjectives

The fix was forcing every claim to trace to a specific, sourced fact, expressed in the posting's own vocabulary rather than a paraphrase, plus an explicit list of things the candidate genuinely does not have experience with that the model is told never to claim and never to apologize for. Silence on a real gap reads as confident; a vague dodge reads as evasive. The closing line changed from a passive wish to a specific, time-bound ask, because a recruiter can say yes or no to "could we do a fifteen-minute call this week," and cannot easily act on "I look forward to hearing from you."

Third pass: coverage versus brevity, on purpose

A conventional cold-email rule is to keep it under 150 words and pick two or three highlights. That is correct advice for a generic recruiter skim, and it is the wrong shape for a posting whose requirements list is long, specific, and clearly written by the person who will actually read the response, not a keyword filter. For that kind of posting, comprehensive, explicit coverage of every listed requirement, including an honest admission where something is genuinely missing, reads as attentive rather than long. The right length depends on who is reading, which is not something a fixed word-count rule can know on its own.

Fourth pass: a second model call that argues with the first

The single biggest quality jump came from splitting generation into two separate calls instead of one. The first call drafts. The second call is handed only the draft and the original posting, and is told to read it as a specific, skeptical recipient deciding whether to reply, then revise anything that fails that read. A model critiquing text it did not just write catches problems it reliably misses while still composing, in the same way a second pass of your own writing the next morning catches things the first pass could not see. 

draft = generate(posting, resume_facts)
final = critique_and_revise(draft, posting)  # separate call, adversarial framing

06Closing the loop without overreaching

An early version of the scheduled routine also scanned the user's inbox for application-confirmation emails and used them to automatically mark postings as applied. It worked, technically, but it moved a decision that belongs to the user into a background process making judgment calls about what an email "counts" as, with no review step. The better design keeps status changes as an explicit, user-driven action inside the dashboard, and treats an automated inbox scan as a feature to reach for deliberately rather than a default running silently underneath everything else. Automating the mechanical parts is the goal; automating the decisions is a different, much riskier thing, and the two are easy to blur together if you are not paying attention.

07Running unattended

The scrape-score-publish cycle runs on a schedule as a cloud agent with its own isolated checkout of the project repository, rather than depending on a machine staying on. State (which postings have been seen, how they scored) is committed back to the repository after each run, which is what makes the scheduled runs actually additive instead of starting from zero every time. The resume itself never travels with the code: a separate local-only step extracts just the skill keywords the scoring step needs into a small file with no personal information in it, and that is the only resume-derived artifact that is version-controlled or reachable by the scheduled job.

08Lessons

  • A heuristic score is a triage tool, not a verdict, and the UI should say so plainly rather than presenting a percentage with false precision.
  • Specificity beats highlight-reeling. Naming the exact term a posting used consistently reads as more credible than a paraphrased, safer-sounding category.
  • An admitted gap is more persuasive than an evasive one. Silence around something a careful reader would notice reads as hiding it; saying it directly reads as confidence.
  • A second, adversarially framed model call is worth the extra latency. Self-critique in a single pass is weaker than a genuinely separate read of already-written text.
  • Automate the mechanical steps; keep a person on every decision that leaves the system or changes what a human believes happened. It is tempting to automate both, and only one of them is actually a good idea.
  • Keep personal data out of anything that has to be portable. Extracting facts instead of committing source documents made the pipeline safely runnable in a separate cloud environment.
